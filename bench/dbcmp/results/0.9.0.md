# tsdb 0.9.0 benchmark results (2026-11-04)

The release benchmark compares tsdb 0.9.0 with ClickHouse, VictoriaMetrics, QuestDB, TimescaleDB, InfluxDB 2 and 3,
Apache IoTDB, TDengine and Prometheus (as servers), and with DuckDB and chDB (embedded). Measuring ended on
2026-11-04 at 03:07.

The full tables, with every measurement, its spread, the number of runs, the memory peaks and how each system was set
up, are in [0.9.0-tables.md](0.9.0-tables.md). This page picks out the main numbers. Every number here comes from a
row of that file.

Queries that tsdb answers from its stored statistics alone (such as a count over all the data, or whole days in UTC)
are left out here, because they measure a lookup, not reading data. They are still in the full tables.

## How it was run

- One machine: AMD Ryzen 9 7950X (16 cores, 32 threads), 64 GB RAM, NVMe disk (ext4 on LUKS), CPU governor
  "performance". One system at a time; every server in Podman, bound to 127.0.0.1.
- Memory: every server ran in a container (tsdbd in a systemd scope) with a hard memory limit and no swap. A server
  that runs out of it, or refuses a query because of it, is shown as such: that is a result, not a missing number.
  The limits actually used:

  | phase | limit |
  |---|---|
  | 100 million rows (queries, time-weighted averages, memory) | 48 GB for every server, tsdbd too, except InfluxDB 2: 24 GB (its highest use was 8.3 GB, so the limit never mattered). InfluxDB 3 ran at 48 GB, after an earlier attempt at 28 GB |
  | size per kind of sensor | 48 GB, except InfluxDB 2 and TDengine 24 GB, InfluxDB 3 28 GB, TimescaleDB 24 GB |
  | embedded | DuckDB's own memory_limit 24 GB; no limit set for tsdb and chDB |

  Some servers also have a limit of their own below the container's: ClickHouse refuses a query above 43.2 GiB (90%
  of the container), QuestDB above its own RSS limit, IoTDB when its query memory pool is full.
- Every answer is checked against tsdb's before it is timed. A system whose answers differ is not timed for that
  query (this happened only for linear time-weighted averages in InfluxDB 2 and TDengine, see below).
- Every timing is repeated 5 times. "Median" is the median time of one request, averaged over the 5 runs.
  Throughput is the mean number of requests per second.
- The data: 100 series of sensor readings, 1 million readings each (100 million rows), from seven kinds of sensors
  with realistic timing jitter. The 100-billion-row run uses 10,000 series of 10 million readings.
- "Batch of 100" means one request asks about 100 series. tsdb answers that as one request; SQL databases get one
  query for the 100 series.
- "Clients" is how many connections ask at the same time. A system that ran out of memory at 32 clients was timed
  again at 16 clients, and so was tsdb: that row is the like-for-like comparison (see
  [When a system ran out of memory or refused](#when-a-system-ran-out-of-memory-or-refused)).
- tsdb: version 0.9.0 on disk format 8. Its rows were measured again on format 8 at the end (its answers were
  identical to the format-7 ones); the older rows are not used.

## Time-weighted averages

ClickHouse, TimescaleDB and the others have no time-weighted average over buckets with the readings carried across
bucket edges; they get the same calculation written in SQL. VictoriaMetrics' query language has none (its
`integrate()` is a step integral without the covered time). InfluxDB 2's `timeWeightedAvg` interpolates only inside
each bucket, so a third of its linear buckets differ from tsdb's: not timed. TDengine's linear form differs in 1,583
of 339,774 buckets: not timed either. Every answer timed here agreed with tsdb's.

## 100 billion rows: tsdb and ClickHouse

10,000 series x 10 million readings, loaded by 8 streams. ClickHouse's queries ran after its background merges had
settled. tsdb on disk format 8 (measured again on 2026-11-04). Both times to "settled" count from the start of the
insert.

| | tsdb | ClickHouse |
|---|---:|---:|
| size on disk | **137.8 GB** (1.38 bytes per row) | 212.1 GB (2.12 bytes per row) |
| insert | **1,480 s** (67.6 M rows/s) | 1,937 s (51.6 M rows/s) |
| insert until merges settled | **3,867 s** | 4,507 s |

Median time of one query, tsdb over TCP:

| query | rows | tsdb | ClickHouse |
|---|---:|---:|---:|

| one series by hour | 10 M | **17.4 ms** | 42 ms |
| one series by minute | 10 M | **29.0 ms** | 54 ms |
| 100 series by day, Europe/Oslo (\*) | 1 G | **122 ms** | 1,071 ms |
| 100 series by hour | 1 G | **398 ms** | 1,100 ms |

(\*) Mostly answered from the statistics tsdb keeps per block of 8192 readings: the blocks inside the window (or the

ClickHouse's times are whole milliseconds (what its benchmark tool reports), so its small queries are approximate.

## When a system ran out of memory or refused

Every failure below is a result: the system was given 48 GB (ClickHouse refuses at 43.2 GiB of its own accord) and
the same requests as tsdb. tsdb never used more than 2.2 GB. Where a system failed at 32 clients, the 16-client run
of the same class, for that system and for tsdb, is the comparison.

| system | what failed at 32 clients | why | at 16 clients (tsdb at 16) |
|---|---|---|---|
| ClickHouse | 100 one-week time-weighted averages | 3 of 5 runs refused by its own memory limit (Code 241: 43.2 GiB), the other 2 failed; it peaked at 43.1 GB (43.9 with the file cache) | 10,985 ms (tsdb 279 ms) |
| QuestDB | one day of 100 series | all 5 runs refused: "global RSS memory limit exceeded" (its own limit); 19.4 GB in use, 15.7 GB held from earlier queries | 2,750 ms (tsdb 18.3 ms) |
| QuestDB | one week of 100 series | all 5 runs refused, its RSS limit | refused again in all 5 runs |
| QuestDB | 100 one-day time-weighted averages | refused: "table busy [reason=pool size exceeded]", its pool of table readers ran out, not its memory | refused again |
| QuestDB | 100 one-week time-weighted averages | failed its answer check at one client (Java heap space) | not run |
| QuestDB, Parquet | one day / one week of 100 series | 1 and 3 of 5 runs killed by the kernel at 48 GB | day: 1 of 5 runs failed ("could not mmap"); week: the server dropped the connection |
| QuestDB, Parquet ZSTD | one day of 100 series | 1 of 5 runs killed by the kernel at 48 GB (peak 39.3 GB) | 9,762 ms (tsdb 18.3 ms) |
| QuestDB, Parquet ZSTD | one week of 100 series | not timed at 1 or 32 clients (no result files) | timed out after 60 s |
| TimescaleDB | one week of 100 series | the server was killed by the kernel at 48 GB twice, so the class was stopped | 5,771 ms (tsdb 74.3 ms), with one run killed and repeated |
| TimescaleDB | 100 one-day and 100 one-week time-weighted averages | the server was killed by the kernel at 48 GB in every run | killed again, with 2, 1 and 0 parallel workers per query |
| IoTDB | one day / one week of 100 series | refused by its own memory pool (code 719: "not enough memory to execute current fragment instance") | not run |
| InfluxDB 3 | 10 one-week windows | killed by the kernel at 48 GB in 4 of 5 runs | not run |
| TDengine | 100 one-day time-weighted averages | no run finished (status -1); memory at the 48 GB limit | not run |

VictoriaMetrics, InfluxDB 2 and tsdb finished every class at 32 clients. TimescaleDB's 16-client aggregate runs used
2 parallel workers per query (the setting that survived a probe); at 32 clients it ran out of memory at every setting
tried, so it ran with its defaults.

The 16-client pass covered tsdb, ClickHouse, QuestDB and TimescaleDB, the systems that failed at 32 clients when it
was planned.
