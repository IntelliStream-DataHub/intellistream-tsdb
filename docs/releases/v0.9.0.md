tsdb 0.9.0 is the first release of tsdb, an embedded time series database written in C, with a server (`tsdbd`) and clients for C, Rust, Python and Java. It stores series of (time in milliseconds, value) points, such as sensor readings, and reads them back as raw points or as summaries per time bucket. It uses a MergeTree-style storage design (immutable sorted parts, merged in the background) and has no SQL and no tables. You can link it into your program as a library or run `tsdbd` and talk to it over TCP. It is built for the backend of a system, on a trusted network.

## Highlights

- **Value types:** float32, float64, int64, bool and state (a text label from a small set). Any value may be null. Writing a value for a time that already exists replaces it (last write wins).
- **Compression chosen per block:** fixed point, XOR, byte split, bit-packed deltas, a dictionary codec and ZSTD. This takes about 1.2 bytes per row on mixed sensor data. On the 31 data sets in BENCHMARKS.md the median is 0.78 bytes per reading, 2.9 times smaller than ClickHouse's median on the same data.
- **Queries:** raw points (oldest or newest first, with a limit), count/sum/min/max/average per bucket (fixed buckets, or calendar buckets in a time zone), the spread (range, standard deviation, variance), LTTB downsampling and time-weighted averages. Where a bucket covers whole granules, the answer comes from stored statistics instead of decoding the data.
- **Many series in one request:** `tsdb_query_multi` answers up to 65,536 series from one snapshot, with a status for each series. A query scheduler shares the CPUs between concurrent queries, and answers are bit-identical at any thread count.
- **Partition classes:** a slow series gets partitions of 7, 28 or 364 days instead of 1 day. A disk temperature read every minute takes 0.268 instead of 0.326 bytes per reading, with queries as fast as before.
- **Durable writes:** a write is on disk when it returns (WAL with group commit, or a periodic sync), and a failed fsync stops the engine. `make jepsen` tests this with kill -9, simulated power loss, injected I/O errors and misdirected or damaged data. The claim it checks is that tsdb answers correctly or reports the damage.
- **Logins and rights:** `tsdbd` requires a login (SCRAM-SHA-256) and gives each user `read`, `insert`, `delete` or `admin` rights on all series, a name prefix (a tenant), one series or a name pattern. Tenant admins manage the users under their own prefix.
- **Server:** one event loop on io_uring or epoll (epoll is chosen by itself where io_uring is disabled, as on AlmaLinux 10 and RHEL 10). Compressed, packed inserts send about 6 bytes per point. Prometheus metrics are served on a port of their own.
- **Clients and bindings:** clients of `tsdbd` in C, Rust, Python and Java with the same operations. Embedded bindings without a server: Rust `Db`, Python `Db` and Java 22+ `EmbeddedDb`.
- **Command line and backups:** `tsdb` creates series, inserts, queries, deletes, sets retention, adds volumes and optimizes. `tsdb export` and `tsdb import` write and read a versioned, checksummed stream of a whole database or some series. Every later tsdb reads every stream an earlier one wrote.
- **Followers and volumes:** one writer, plus any number of read-only followers on other hosts over NFS. A database can span several volumes (directories or mounts).
- **Apache Pulsar 5 sink** (`connectors/pulsar`): Pulsar holds the points while tsdb is down, and a point is taken off Pulsar once it is on disk.
- **Benchmarks:** in the comparison in BENCHMARKS.md (100 million readings, one machine, each timing repeated 5 times) tsdb loaded 85.8 M rows/s over TCP against 47.5 M rows/s for ClickHouse. tsdb syncs every write to disk before it answers; ClickHouse does not. The full setup and the other databases are in [BENCHMARKS.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.0/BENCHMARKS.md).

## Formats

| | version |
|---|---|
| Disk format | 8 |
| Wire protocol | 12 (the server and the clients refuse a peer below 12) |
| Embedded C ABI | 3 |

Series ids are 64 bits. Before 1.0, a 0.9.x release may still change the disk format and the wire protocol, with export and import or a migration to carry data over; they freeze at 1.0. See [docs/compatibility.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.0/docs/compatibility.md). A database of another disk format version is refused at open, with a message that names both versions. Use the same release on the server and its clients: clients and servers of different 0.9.x releases may not understand each other.

Nothing was released before 0.9.0, so there is nothing to upgrade from. If you ran a development build, a database of disk format 5, 6 or 7 is carried over with `tsdb export` (the build that wrote it) and `tsdb import` (this release).

## Security and limits

- **Login is required by default.** `tsdbd` does not start while the database has no superuser; add one with `tsdb <dir> user add NAME --superuser`. `--no-auth` turns logins off, so that every client may do everything; use it only for tests and on your own machine.
- **No TLS yet.** Data, queries and login exchanges travel in the clear. A recorded login does not show the password, but a recorded password change plus a later recorded login of the same user is enough to log in as that user, and someone who can change traffic can take over a connection after its login. Until TLS exists, a login does not protect you on a network you do not trust; change passwords on the server host (`tsdb <dir> user passwd`). Keep `tsdbd` on an isolated backend network (it listens on 127.0.0.1 unless you pass `--listen`).
- **The metrics port has no login.** Bind it to a trusted interface (`--metrics-bind`).
- **The library and `tsdb <dir>` commands need no login**: they open the files directly, and the file permissions decide.
- **Damaged data:** without `--verify-checksums`, a damaged granule reads as wrong values. On ext4 and XFS, which keep no data checksums, turn it on; `tsdbd` says so at startup.
- **One writing server per database.** Followers are read-only; automatic failover is not built. There is no SQL and there are no latest-value lookups or series metadata.

The full list is in [SECURITY.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.0/SECURITY.md), including how to report a vulnerability.

## Install

Download `tsdb-0.9.0-x86_64-linux.tar.gz` and `tsdb-0.9.0-x86_64-linux.tar.gz.sha256` from the assets of this release, and check the tarball against the checksum in the second file:

```
sha256sum -c tsdb-0.9.0-x86_64-linux.tar.gz.sha256
```

GitHub Actions built the tarball from the tag `v0.9.0`, ran its test suite, and published a signed build provenance attestation for it (on the repository's Attestations page).

The tarball runs on x86-64 Linux with glibc 2.34 or newer and an x86-64-v2 CPU or newer (Intel Nehalem and later, AMD Bulldozer and later). It picks faster code at startup on CPUs with AVX2 or AVX-512, and gives the same results on every CPU. It has been tested on AlmaLinux 10 and under an emulated Westmere and Sandy Bridge. Unpack it, optionally run `tests/run-tests.sh`, and start `bin/tsdbd`; the tarball's `README.dist` has the details and a systemd unit. Other platforms build from source.

To build from source or follow the five-minute walk-through, see [Getting started and the quick start in the README](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.0/README.md#quick-start-5-minutes-one-machine).
