tsdb 0.10.0 is a minor release of tsdb, an embedded time series database written in C, with a server (`tsdbd`) and clients for C, Rust, Python and Java. It **changes the disk format (to 9) and the wire protocol (to 14)**, so **a 0.9.x database needs one step before this release opens it** (below). It adds the latest value of every series, statistics of what is stored, the disk side of a change feed and the first build of a cluster's metadata group. **The change feed is off by default and the cluster is a preview**; neither is meant for production yet.

## Moving a 0.9.x database to 0.10.0

0.9.0 and 0.9.1 wrote disk format 8. This release reads format 9, refuses a format-8 database (the message names both versions and the command), and a 0.9.x binary refuses a format-9 database in the same way, so an upgraded database cannot be opened by the old release. Keep an export or a copy until the new release has run for a while.

1. Stop `tsdbd`, and every follower on other hosts, and make sure the database was shut down cleanly (no WAL segment left behind).
2. Run `tsdb DIR upgrade` with this release. It carries the database over in place (new `FNO`, `MANIFEST` and `META` files for each volume, the root last) and can be run again if it died. It refuses, and says why, if the database was not closed cleanly.
3. The parts keep their old 24-byte headers until merges rewrite them (`tsdb DIR optimize` does it at once); `META` says `parts_v8=1` until none is left. Before 1.0 that allowance goes: run 0.10.x until the open reports none left, or export and import.

Export and import always work instead: `tsdb DIR export -o FILE` with the old release, `tsdb NEWDIR import FILE` with this one. Do not run the old release's `tsdb` (`volume add` above all) on an upgraded database.

## Added

- **The latest value of every series**: `tsdb_latest` in the library (backed by a per-volume table that is kept exact and filled in the background; `latest_cache` sets its memory, `tsdbd --latest-cache BYTES`), `QUERY_LATEST` on the wire (protocol 14, up to 1,048,576 series per request, rights checked per series), `latest` and `latest_by_name` in all four clients and the embedded bindings, and `tsdb DIR latest NAME...` in the CLI.
- **Statistics of what is stored and of what queries did**: rows, nulls, bytes by kind, parts, granules and last write per series, per volume and per tenant (a name prefix); the hottest series; sampled page-cache residency; query counters. In the embedded API and the CLI (`tsdb DIR stats`, `stats series`, `stats tenants`, `stats hot`); the server adds them to its metrics port (docs/metrics.md) and has `--no-stats`. Nothing is added to the write path, and there are no per-tenant metrics.
- **Reply bodies for the failover cases (protocol 13)**: `UNAVAILABLE`, `MOVED`, `PARTIAL` and `DROPPED` carry a body, two ops `TOPOLOGY` and `STATUS` exist, and all four clients decode them, retry `UNAVAILABLE` within a time budget and connect to a list of nodes. `tsdbd` sends only `UNAVAILABLE` today (for volumes of a storage domain that is down); the rest is for the cluster. A client of protocol 12 still reads the bare status codes.
- **Change feed, step 1 (off by default)**: `tsdb DIR feed enable|disable|info|new-id` keeps the WAL segments the engine no longer needs (24 hours or 64 GiB per volume by default, and never when the disk has less than 10% free). With the feed off nothing changes on disk or in timing. **Nothing reads the kept segments yet**: there is no reader, no wire op, and the status codes reserved for it are never returned.
- **Cluster metadata group (preview)**: `tsdbd --cluster` joins servers into a Raft group on a peer port of its own and `tsdb cluster init|node add|status|secret` manage it. This is the group and its state machine only: **it does not replicate data, move a volume or fail over**, it does not change what a request does, and its metadata formats may still change before 1.0. Do not run it in production. Without `--cluster` none of it runs.

## Fixed

- Appends and lookups no longer stall for 8 to 20 ms when a memtable flushes at a million series (worst append 13.5 ms to 0.84 ms in the benchmark; the append median goes from 2 to 4-5 microseconds).
- A damaged part is a barrier inside its partition, not a stop for all of it: the ranges on either side keep merging, so the part count of the partition stays bounded.
- A WAL segment whose removal failed while the database was opened was counted as removed, which could let an empty merge output be dropped and deleted rows come back at the next open.
- `tsdbd`: a slow reader needs a minimum rate (16 KB/s over the send timeout), not just any movement; a query streaming to a slow client no longer holds up a volume's recovery; rights are checked before a volume's domain is looked at, so a denied user cannot learn which volumes are down; volume recovery checks the volume number and root id of the directory before it writes anything, and name lookups no longer keep a recovery waiting.
- The jepsen power nemesis's "was idle" check no longer fails under machine load without a violation.

## Formats

| | version |
|---|---|
| Disk format | 9 (0.9.0 and 0.9.1 wrote 8; `tsdb DIR upgrade`, or export and import) |
| Wire protocol | 14 (13: HA reply bodies; 14: QUERY_LATEST); the floor stays 12, so clients and servers of 12 still talk to it |
| Embedded C ABI | 7 (3 in 0.9.x: rebuild embedded programs; the Rust and Java bindings check it) |

Before 1.0, a 0.x release may still change the disk format and the wire protocol; they freeze at 1.0. See [docs/compatibility.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.10.0/docs/compatibility.md). Use the same release on the server and its clients.

## Security and limits

The notes of 0.9.0 and 0.9.1 still hold: login is required by default; there is no TLS, so keep `tsdbd` on an isolated backend network; the metrics port has no login; one writing server per database; without `--verify-checksums` a damaged granule reads as wrong values. The cluster port (`--peer-port`) authenticates peers with a shared secret and is not encrypted either. The full list is in [SECURITY.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.10.0/SECURITY.md) and in the known limitations of the changelog.

## Install

Download `tsdb-0.10.0-x86_64-linux.tar.gz` and `tsdb-0.10.0-x86_64-linux.tar.gz.sha256` from the assets of this release, and check the tarball against the checksum in the second file:

```
sha256sum -c tsdb-0.10.0-x86_64-linux.tar.gz.sha256
```

GitHub Actions built the tarball from the tag `v0.10.0` and ran its test suite there (at every CPU level the build machine has), in AlmaLinux 10, and under an emulated Westmere and Sandy Bridge; the build's provenance is attested.

The tarball runs on x86-64 Linux with glibc 2.34 or newer and an x86-64-v2 CPU or newer (Intel Nehalem and later, AMD Bulldozer and later). It picks faster code at startup on CPUs with AVX2 or AVX-512, and gives the same results on every CPU. Unpack it, optionally run `tests/run-tests.sh`, and start `bin/tsdbd`; the tarball's `README.dist` has the details and a systemd unit. Other platforms build from source.

To build from source or follow the five-minute walk-through, see [Getting started and the quick start in the README](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.10.0/README.md#quick-start-5-minutes-one-machine).
