tsdb 0.9.1 is a patch release of tsdb, an embedded time series database written in C, with a server (`tsdbd`) and clients for C, Rust, Python and Java. It fixes **two ways in which data could be lost or come back**, makes `tsdbd` survive outages of NFS storage, and adds macOS as a platform for developers. The disk format (8), the wire protocol (12) and the embedded C ABI (3) are the same as in 0.9.0: a database written by 0.9.0 opens as it is.

## Fixed: data

- **A deleted partition could come back after a crash.** `tsdb_drop_before` (and retention, which drops an expired partition) acknowledged the delete, but a merge of that partition that was already running had written its result before it saw the delete, and only unlinked it. After a kill -9 or a power loss, the next open listed that result with every deleted row. A drop now waits for a merge of its partition, no new merge starts in it meanwhile, and the files of dropped and replaced parts are renamed to `retired_` before the directory is synced, at every `obsolete_part_lifetime_s` (at 0 or less the deleted rows also came back after a crash).
- **Inserts could wait for ever on a partition with a damaged part.** An insert that leaves a partition with more than 300 parts waits for merges. A merge that failed on a damaged granule was retried every second and the part count never fell, so every insert into the partition, and every worker of `tsdbd`, waited for ever. Now the part is marked (logged once, counted in `tsdb_broken_parts`) and left out of merges, and the wait ends at once for such a partition, and after 30 seconds without progress for any other (a full disk, parts that cannot pair). The insert still succeeds, because its rows are published before the wait. Restore a part that is reported damaged from a backup.

## Fixed: server

- A connection whose output has not moved for `--send-timeout` seconds is closed even when its whole reply fit in the server's buffers; before, a client that sent a query and never read the answer held up to about 17 MB per connection.
- A client that keeps reading a large reply, only slowly, is no longer cut: the timeout counts progress, not the time since the reply began. Time the server itself was stopped does not count against `--send-timeout`, `--frame-timeout` or `--login-timeout`.
- The time retired parts live (`obsolete_part_lifetime_s`) is counted on the monotonic clock: a step of the wall clock (NTP, a resumed VM) no longer deletes them at once, while a follower on another host may still have them mapped.
- `tsdb_query_multi` checks the bounds of a bounds query once per call, not once per series (65,536 series over the bounds of one frame took about 250 s), and answers `TSDB_ERR_INVALID` for bounds that do not strictly increase, as the single-series call does. It also claims its first series before it wakes helper threads, so the first answer is no longer computed twice.
- `volume add` refuses a directory that holds a file the volume would take for one of its own (a WAL segment, a part, `STATES`, ...), instead of cutting, replaying or deleting it at the first open.

## Added

- **Storage outages on NFS** (`tsdbd --health-domain PREFIX`, once per NFS server or filesystem). Each domain is probed and is UP, DEGRADED, DOWN or RECOVERING. Requests for a volume of a DOWN domain answer `TSDB_ERR_UNAVAILABLE` (new status -11, meaning not applied, try later) at once, and the other volumes go on. A write or sync error on such a volume no longer ends `tsdbd`: the volume is stopped, reopened from what is on disk and checked, and a volume that lost acknowledged data stays stopped and says which. This is the first step, with limits (no discovery of domains, no metrics yet); see [docs/tasks/nfs-outage.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.1/docs/tasks/nfs-outage.md). The clients show -11 as "unknown error" with the code.
- **macOS (Apple silicon and Intel) as a developer platform**, not for production: `make`, `make test IO=epoll` and `make test-clients` work there. See [docs/macos.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.1/docs/macos.md).
- `tsdb_latest`, the newest row of each of many series, in the embedded API (not yet in `tsdbd` or the clients).
- `tsdbd --lttb-max-threshold` (default 16,777,216): the largest LTTB threshold the server computes, so that a threshold near the rows of a huge series cannot hold gigabytes for one request.
- More fuzz harnesses, and CI that builds, tests and attaches the release tarball of a pushed tag.

## Formats

| | version |
|---|---|
| Disk format | 8 (as in 0.9.0) |
| Wire protocol | 12 (as in 0.9.0; the server and the clients refuse a peer below 12) |
| Embedded C ABI | 3 (as in 0.9.0; functions and structs were added) |

Before 1.0, a 0.9.x release may still change the disk format and the wire protocol; they freeze at 1.0. See [docs/compatibility.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.1/docs/compatibility.md). Use the same release on the server and its clients.

## Security and limits

The notes of 0.9.0 still hold: login is required by default; there is no TLS, so keep `tsdbd` on an isolated backend network; the metrics port has no login; one writing server per database; without `--verify-checksums` a damaged granule reads as wrong values. The full list is in [SECURITY.md](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.1/SECURITY.md) and in the known limitations of the changelog.

## Install

Download `tsdb-0.9.1-x86_64-linux.tar.gz` and `tsdb-0.9.1-x86_64-linux.tar.gz.sha256` from the assets of this release, and check the tarball against the checksum in the second file:

```
sha256sum -c tsdb-0.9.1-x86_64-linux.tar.gz.sha256
```

GitHub Actions built the tarball from the tag `v0.9.1` and ran its test suite there (at every CPU level the build machine has), in AlmaLinux 10, and under an emulated Westmere and Sandy Bridge; the build's provenance is attested.

The tarball runs on x86-64 Linux with glibc 2.34 or newer and an x86-64-v2 CPU or newer (Intel Nehalem and later, AMD Bulldozer and later). It picks faster code at startup on CPUs with AVX2 or AVX-512, and gives the same results on every CPU. Unpack it, optionally run `tests/run-tests.sh`, and start `bin/tsdbd`; the tarball's `README.dist` has the details and a systemd unit. Other platforms build from source.

To build from source or follow the five-minute walk-through, see [Getting started and the quick start in the README](https://github.com/IntelliStream-DataHub/intellistream-tsdb/blob/v0.9.1/README.md#quick-start-5-minutes-one-machine).
