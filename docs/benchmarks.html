Benchmarks

How tsdb 0.11.0 compares with eleven other databases on the same machine and the same data, plus new v0.11.0 measurements for SIMD codec throughput across three CPUs and durable multi-node cluster ingestion. Every number here comes from the published 0.11.0 results (other databases: unchanged 0.9.0 baselines on the same hardware).

How it was measured

  • One machine: AMD Ryzen 9 7950X (16 cores, 32 threads), 64 GB RAM, NVMe disk. One system at a time; every server in a container with the same hard memory limit of 48 GB (InfluxDB 2: 24 GB, and it used at most 8.3 GB). tsdb 0.11.0 was re-measured on disk format 9 (with UTC hour-cut granules and AVX-512 SIMD codecs enabled) against the exact same input files and query suites.
  • The data: 100 sensors with 1 million readings each, 100 million readings in all, from seven kinds of sensors that behave like real ones (temperatures that creep, tanks that fill and drain, a fast vibration sensor, flows with shutdowns). The size test adds 23 real sensors from a hydraulic test rig: 31 data sets.
  • Every answer was checked against tsdb's before it was timed (tsdb 0.11.0 verified 0 mismatches against the 0.9.0 reference dumps). Every timing was repeated 5 times; a time is the median time of one request. tsdb ran as a server, over TCP with io_uring.
  • We left out the questions tsdb answers from the summaries it stores, such as a count over all the data: they measure a lookup, not reading data. Every question below reads the data.
  • A system that ran out of memory or refused a request is shown with the reason. That is a result, not a missing number.

Servers: 100 million readings

100 sensors with 1 million readings each. tsdb ran as a server, over TCP. Ingest is 100 million rows divided by the load time: tsdb syncs every write to disk before it answers; ClickHouse, VictoriaMetrics and QuestDB do not. Read is all 100 sensors over the whole history in buckets of 60 readings, in one request. Max memory is the most each server held without the file cache over the runs that finished, the 16-client runs included; a red tag marks a system that failed with 32 clients asking about many sensors at once.

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. * QuestDB open source, in its default format, which does not compress. It compresses only partitions you convert to Parquet by hand (with ZSTD 1.02 bytes per reading; converting took 28 minutes); automatic conversion is Enterprise only. Exact numbers: BENCHMARKS.md.

Embedded: a library inside your program

The same 100 million readings in one process, with no network. chDB is ClickHouse as a library. Read is random days of one sensor in 5-minute buckets, one call at a time: tsdb uses one thread per call, chDB and DuckDB 32. DuckDB got its readings sorted beforehand (not counted).

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. Exact numbers: BENCHMARKS.md.

100 billion readings: tsdb and ClickHouse

0.9.0 baseline: 10,000 sensors with 10 million readings each, loaded by 8 streams. Read is the whole table in hourly buckets.

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. Exact numbers: BENCHMARKS.md.

Codec throughput across CPUs (v0.11.0)

Version 0.11.0 adds AVX2/AVX-512 bit-unpacking kernels, faster prefix-sum and decimal reconstruction, and format-9 encodings for integers, booleans, states and jittery timestamps (see Compression). Multi-node cluster ingestion (v0.11.0)

Version 0.11.0 adds replicated cluster volumes and native InfiniBand RDMA peer links. In the 4-node all-NVMe cluster, InfiniBand RDMA reduced worst-node p99 latency by 29% (compressed) and 39% (raw) while sustaining up to 64.4 M net replicated rows/s on a single leader node. In the 5-node mixed cluster, synchronous ISR durability means any volume placing a replica on the SATA SSD runs at SATA fsync speed while volumes placed purely on NVMe run at full NVMe speed.

Measure it yourself

Clone the repository and run tools/bench-tsdb.sh --quick first to see that it works. It builds an optimized copy, runs tsdb's own benchmarks several times and writes a summary with the mean and spread of every number. The comparison with the other databases is in bench/dbcmp; the v0.11.0 record is in 0.11.0.md, and every single 0.9.0 baseline measurement is in 0.9.0-tables.md.
