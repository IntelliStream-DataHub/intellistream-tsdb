Cluster preview

Release 0.10.0 has the first piece of tsdb's cluster: a small group of servers that agree on who the members are. This page sets one up on one machine, looks at it, kills the leader and starts it again. About ten minutes.

What this is, and what it is not

The metadata group is a few servers that agree, with the Raft protocol, on a list of facts: which servers are members, whether they are up or down, which are voters (they decide) and which only watch, and the settings of the cluster. A witness is a member with no data: it keeps the list and can vote, a cheap third or fifth vote. The group also has places for volumes, owners, epochs, in-sync sets, users and grants, which later steps fill.

It is a preview. It does not copy your data: a row written to one server stays on that server. It does not fail over: when a server dies, the group marks it down and nothing takes over its data. It does not move volumes, and you cannot add a volume or a user to the cluster yet. It changes nothing for clients: the client port, the protocol and every request work as without --cluster, and logins stay per server. Do not run it in production. The metadata format and the peer protocol may change in a later 0.x release; you then start the cluster again with tsdb cluster init, you do not upgrade it.

Why ship it? The group is the part everything else stands on, and the hardest to get right. It has its own simulator, a checker and fault tests, and now you can run it yourself. Without --cluster none of it runs.

What you need

  • A checkout of tsdb, built with make (the first step does it). Linux, no root.
  • Three free ports for the servers' clients (17081 to 17083; the witness of step 9 has none) and four for their peers (17091 to 17094) on 127.0.0.1. If something else uses one, change the numbers in the two lines marked # ports in step 3: they are the only place where the block writes a port.
  • Nothing else. The block only writes under /tmp/tsdb-cluster.

The tutorial

Paste the whole block into a terminal, in the top directory of the checkout. It stops at the first command that fails. Our tests run it word for word, so it works as written.

# 1. Build. Everything lands in build/.
make

# 2. A scratch directory, and the cluster's secret. The secret is a file with 32 random bytes written as hex
#    (mode 0600). Every server and every `tsdb cluster` command reads it. Whoever has it can change the cluster.
D=/tmp/tsdb-cluster
rm -rf $D && mkdir -p $D
build/tsdb cluster secret $D/secret

# 3. Helpers. A "node" is a server with its own data directory (n1/data) and its own state directory (n1/state).
#    The state directory holds the cluster's own files and must be on a local disk, never on NFS.
#    Node N listens for clients on port 1708N and for the other servers on port 1709N (the two lines marked ports).
#    --no-auth: no login, because users are still per server in the preview. Fine on 127.0.0.1, nowhere else.
#    A witness (node 4) has no data directory and no client port.
port() { echo 1708$1; }                    # ports: the client port of node N
pport() { echo 1709$1; }                   # ports: the peer port of node N
peer() { echo 127.0.0.1:$(pport $1); }     # the peer address of node N
start_node() {                             # start_node N [witness]: start a server, remember its process id
    mkdir -p $D/n$1/state
    if [ "${2:-}" = witness ]; then role="--witness --advertise 127.0.0.1"
    else mkdir -p $D/n$1/data; role="--dir $D/n$1/data --no-auth --port $(port $1)"; fi
    build/tsdbd $role --state-dir $D/n$1/state --peer-port $(pport $1) \
        --cluster --cluster-secret-file $D/secret --rack rack$1 >> $D/n$1/log 2>&1 &
    echo $! > $D/n$1/pid
}
status() { build/tsdb cluster status $(peer $1) --secret-file $D/secret; }    # status N: ask node N
wait_for() {                               # wait_for N REGEX: wait (30 s at most) until node N's status has such a line
    for i in $(seq 150); do status $1 2>/dev/null | grep -q "$2" && return 0; sleep 0.2; done
    echo "gave up waiting for: $2"; return 1
}

# 4. Start three servers. They know nothing of each other yet: each one says it is in no cluster.
start_node 1; start_node 2; start_node 3
for n in 1 2 3; do wait_for $n '^node'; done
status 1

# 5. Make the cluster on node 1 (it becomes node 1 and the leader), then add the other two through it.
#    The group grows by itself: one voter, then three. Wait until all three vote, then look at it from node 2.
build/tsdb cluster init $(peer 1) --secret-file $D/secret
build/tsdb cluster node add $(peer 1) $(peer 2) --secret-file $D/secret
build/tsdb cluster node add $(peer 1) $(peer 3) --secret-file $D/secret
wait_for 2 '^group voters 1,2,3 '
status 2

# 6. Nothing changed for clients, and nothing is copied. Write a day of readings to node 1 as if it were
#    a lone server, then list the series in node 1's directory and in node 2's.
build/client-example 127.0.0.1 $(port 1)
build/tsdb $D/n1/data series | cut -f1,2
echo "node 2 has $(build/tsdb $D/n2/data series | wc -l) series"

# 7. Kill the leader, as a crash would (kill -9, by its process id). The others elect a new leader, and once that
#    one has led for three seconds (node_timeout_ms) without a heartbeat from the dead node, it marks the node down.
#    Ask a survivor.
leader=$(status 2 | awk 'NR == 1 { print $10 }')
other=$(( leader % 3 + 1 ))
echo "node $leader is the leader: stopping it"
kill -9 $(cat $D/n$leader/pid)
wait_for $other "^member $leader down"
status $other

# 8. Start it again on the same directories. It comes back as the same member with a new incarnation (a counter of
#    its starts), and it is up again.
start_node $leader
wait_for $leader "^member $leader up incarnation 2"
status $leader

# 9. A witness: a member without data. Start it, add it through any member, look at it. With three voters it only
#    watches (the group keeps an odd number of voters); it takes a voter's place when one is lost for good.
start_node 4 witness
wait_for 4 '^node'
build/tsdb cluster node add $(peer 1) $(peer 4) --secret-file $D/secret
wait_for 4 '^member 4 '
status 4

# 10. What the servers said about the leaders and the members' state, from their logs (the details differ on your machine).
grep -h 'leads the metadata group\|proposes node' $D/n[123]/log

# 11. Stop every server by its process id, wait until they are gone, and clean up.
for n in 1 2 3 4; do kill $(cat $D/n$n/pid); done
for n in 1 2 3 4; do while kill -0 $(cat $D/n$n/pid) 2>/dev/null; do sleep 0.1; done; done
rm -rf $D

Step 10 prints what the servers logged about leaders and members. Only the new leader proposes a change, so a line shows in one log only. For example:

tsdbd: cluster: node 2 leads the metadata group (term 2)
tsdbd: cluster: proposes node 1 down (incarnation 1)
tsdbd: cluster: proposes node 1 up (incarnation 2)

The dead node is down only after a few seconds: a server is marked down when the leader has not heard its heartbeat for node_timeout_ms (3 s by default). The survivors first elect a new leader, and it marks the node down once it has itself led for node_timeout_ms, so the down comes a few seconds after the election. When the down line appears, a new leader exists.

How to read status

tsdb cluster status PEER asks one server what it knows and prints one fact per line. Ask any member: they agree, up to a moment's delay. A server that has just restarted may show its saved copy first, with a stale line, until the group has confirmed it.

LineMeaning
node N mode M role R term T leader L commit C applied AThe server you asked. N: its member number (0: in no cluster). M: none, core (it runs a copy of the Raft group: a voter, or a learner on its way to be one) or watch (it follows the group's state without voting). R: follower, pre-candidate, candidate or leader (- outside the group). T: the election term, up by one at every election. L: the leader's number, 0 when it knows none. C, A: how far the log is committed, and how far this server has applied it.
stale ...The copy this server saved before a restart; no one has confirmed it yet.
cluster UUID replication ...The cluster's id and its settings (init fixes them).
group voters 1,2,3 learners -Who votes, and who is catching up to join the vote.
member N STATE incarnation I addr A peer P rack R heard H ...One line per member. STATE: up or down (the group also knows draining and out, which nothing sets in the preview). I: how many times it has started. A: where clients reach it. P: where servers reach it. H: how long ago the server you asked last heard from it. voter_ok and volumes_ok: whether it may vote and may hold volumes (a witness has volumes_ok 0). core_dropped 1: its Raft core was dropped after a log fault; it goes on as a watcher.
volume-report ..., domain-report ...What a member says about its volumes and storage domains. None in the preview: no volumes exist.
volumes N users MHow many volumes and users the group holds. Always 0 in the preview.

How many voters? One with one or two members, three with three or four, five with five or more (at most --voters). A member that does not vote watches.

If something goes wrong

  • "cannot connect to ...: Connection refused": the server is not running (yet), or the address is wrong. Look at /tmp/tsdb-cluster/n1/log. A port that is taken shows there as "cannot listen"; change the numbers in the two lines of step 3 marked # ports, and nothing else.
  • "... is not a cluster peer port with this secret": the address is not a server's peer port, or the secret file differs from the one the server was started with.
  • "the secret file ... is open to its group or to others: refused": chmod 600 it. tsdb cluster secret FILE makes a file with the right mode.
  • "the server is already in a cluster" (from init): stop it, remove its state directory and start it again to start over.
  • "the new server did not answer" (from node add): the server at the new address is not running, or not running with --cluster and the same secret.
  • "the new server belongs to another cluster or has another id" (from node add): the server at the new address is a member of a cluster already. To use it here, stop it, remove its state directory and start it again.
  • The block fails in the middle and servers keep running: stop them by process id: for n in 1 2 3 4; do kill $(cat /tmp/tsdb-cluster/n$n/pid); done. Do not use pkill or killall: they stop every process with that name, also ones that are not yours.
  • Two of the three nodes are gone: the third has no majority. Its role stays pre-candidate, it shows leader 0, and the dead members stay up in its view: nobody is left to mark them down. The group changes nothing until one of the others is back. That is the rule, not a bug.
  • When you are done: rm -rf /tmp/tsdb-cluster.

Reference

The server: tsdbd options

All of these are off without --cluster. The client port, --dir and every other option work as before.

OptionWhat it does
--clusterStart the cluster thread. Needs --cluster-secret-file and --state-dir, and a writer (not --read-only or --follow).
--cluster-secret-file FThe cluster's secret (tsdb cluster secret F makes one). Mode 0600, the same file on every server.
--state-dir DIRWhere the cluster's files live. A local file system, never --dir, never NFS or CIFS (refused).
--peer-port N|0The port other servers and tsdb cluster use. Default: the client port + 1. 0: the system chooses (the fourth number of --port-file).
--peer-listen ADDRThe address the peer port binds to. Default: --listen.
--advertise HOSTThe host other servers and clients are told to use. Default: --listen, which must then not be a wildcard. Needed for a witness.
--rack NAME, --power-feed NAMEWhere the server stands, for placing copies apart later. Shown by status.
--bmc ADDRThe server's management controller, for the bmc failover. Stored; nothing uses it yet.
--read-barrier on|offThis server's read barrier setting, for shared volumes. Default on.
--witnessA member without data: needs --cluster, takes no --dir and has no client port. Give it --advertise, the host the others reach it at. It votes and keeps the group's state.

For scripts: with --port-file F the file says PORT PID MPORT PEER_PORT. Start servers with --port 0 --peer-port 0 --port-file F, as the tests do, and a port is never taken twice.

The command line: tsdb cluster

tsdb cluster with no arguments prints these. The commands talk to a running server's peer address (PEER, host:port), need no directory, keep no state, and authenticate with the secret (--secret-file F).

CommandWhat it does
tsdb cluster secret FILEMake a new secret: 32 random bytes as hex, mode 0600. Never overwrites a file.
tsdb cluster init PEER --secret-file F [options]Make the cluster on one server that is in no cluster yet. It becomes node 1 and the leader. The options fix the settings.
tsdb cluster node add PEER NEW_PEER --secret-file FAdd the server at NEW_PEER (running with --cluster, in no cluster yet). PEER is any member; the command follows to the leader. Adding a member again does no harm.
tsdb cluster status PEER --secret-file FWhat that server knows (see above).

Options of init; each number is a whole number above 0. The settings are stored and shown; in the preview nothing acts on those about volumes and failover yet.

OptionDefaultWhat it does
--replication N3Copies of every volume.
--min-isr N1Copies that must be in sync for a write to count. At most --replication.
--node-timeout-ms MS3000A server is marked down after this long without a heartbeat.
--heartbeat-ms MS500How often servers report. Below --node-timeout-ms.
--isr-lag-ms MS1000A copy this far behind leaves the in-sync set. Stored; nothing acts on it in the preview.
--out-after-s S1800A server down this long is marked out. Stored; in the preview no server is ever marked out.
--voter-replace-s S600A voter down this long is replaced by another member.
--voters N5The most voters the group has (an even number counts as one less).
--volumes-per-server N16Volumes led per server.
--mode replicated|sharedreplicatedServers with their own disks, or volumes on shared (NFS) storage. One mode for the whole cluster.
--failover lease|attested|bmcleaseHow a dead owner is replaced in shared mode.
--read-barrier on|offonOwners answer reads only behind a fenced write (shared mode).
--lease-s S10The lease of a shared volume.

The designs list more commands (node drain and out, volume add and move, user, restore, adopt). They are not built.

What's next

The designs are written; the work goes in this order:

  • The metadata group, finished (steps S2, S4): the servers' links and routing of requests, users and grants kept in the group, and names that are unique across the cluster. The group's state machine (S1) and what a single server does while its storage is away (UNAVAILABLE, N1) are already in 0.10.0; the rules for ownership and time come with N7.
  • Shared mode (N0, N2 to N8): a go/no-go measurement (N0), then failover on NFS storage with one writer per volume, fenced by the group. Production on NFSv4 needs this first.
  • Replicated mode (R1 to R4): each volume on three servers with their own disks, with replication, the in-sync set, promotion and rebuild. Raft stays off the insert path.
  • Then clients that talk to the owner directly, and a cold tier.

Read more on GitHub: design-ha-modes.md (the two modes and the build plan), design-cluster.md (the replicated cluster and the metadata group), ha.md (failover on NFS) and roadmap.md.
