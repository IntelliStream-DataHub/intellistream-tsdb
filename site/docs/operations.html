Operations

What to know when tsdb runs for real: where the data goes, how to read it from other machines, how to guard it against a bad disk, how to watch it, and how to back it up.

Volumes

A database is a directory. A volume is another directory that holds series of their own, for example one per disk or per NFS mount. Each series lives in one volume; you choose it when you create the series.

  • Add one with tsdb DIR volume add PATH, also while tsdbd runs. tsdb DIR volume list lists them, the database directory first.
  • Create a series in it with tsdb DIR create SERIES PATH, or from a client that names the path.
  • Only an operator adds volumes. A client that names a path tsdbd does not know gets "not found", and nothing is created.
  • The path must be absolute, and not inside the database directory or another volume.

Followers, also over NFS

One writer and any number of read-only followers can share a directory. A follower answers queries and sees new data shortly after the writer has it:

build/tsdbd --dir /data/sensors --port 7070
build/tsdbd --dir /mnt/sensors --port 7070 --follow    # a read-only copy that follows the writer

The first line is the writer, the second a follower. The follower looks for new data every 100 ms (--refresh-ms): new parts, merges, and the newest rows from the write-ahead log. The directory can be on NFS, so the followers can run on other machines.

  • When a merge replaces files, the writer keeps the old ones for 8 minutes before it deletes them, so a follower on another machine can finish reading them.
  • Watch tsdb_follow_refresh_age_seconds. Above 5 seconds, the follower has stopped refreshing. It does not tell you that the writer is down; watch the writer for that.
  • An NFS server for tsdb needs some care (sync exports, locks, short leases). docs/nfs-server.md walks through it.

Checksums and the pinned index

tsdb keeps a checksum on every part's header and index, on its write-ahead log and on its small files, and checks them when it opens them. The data blocks themselves are checked only if you ask for it. Whether you should depends on the file system:

File systemStart tsdbd withWhy
ext4 or XFS--verify-checksums, and --pin-index if the RAM is therethey keep no checksums of your data, so without the flag a damaged disk block can come back as wrong values instead of an error. tsdbd reminds you at startup
ZFSnothingZFS checks its data itself

--verify-checksums checks the data each query reads. Each part's index (which rows are where, and the sums, minimums and maximums that queries answer from) is checked when the part is opened, and then read from the file as it is. If the disk damages it after that, answers can be wrong until the next restart refuses the part.

--pin-index keeps a copy of every index in memory, as it was checked, so that cannot happen. The copy costs about 51 bytes of RAM per granule (a block of up to 8192 rows of one series), in the server and in every follower. That is about 4 MB per billion rows of busy series, but at least one granule per series and partition, so with many slow series it adds up: a billion series take about 51 GB per partition. The metric tsdb_pinned_index_bytes shows what it costs. Turn it on where you use --verify-checksums and the RAM is there.

Metrics

--metrics-port 9170 serves GET /metrics in the Prometheus text format on a port of its own. It is off by default and has no login, like the main port: bind it to a trusted interface. A scrape never runs a query. A Prometheus scrape config:

scrape_configs:
  - job_name: tsdb
    static_configs: [{targets: ["db1:9170"]}]

Some of the metrics:

MetricWhat it tells you
tsdb_rows, tsdb_disk_bytes, tsdb_partsrows and bytes on disk, and the number of parts
tsdb_inserted_rows_totalrows written; rate(tsdb_inserted_rows_total[1m]) is the insert rate
tsdb_query_duration_secondsa histogram of query times, by operation
tsdb_memtable_rowsrows in memory, not yet in parts; growing without end means writes to disk do not keep up
tsdb_failed1 once the disk failed and tsdbd stops: alert on it
tsdb_follow_refresh_age_secondsfollowers: time since the last good refresh
tsdb_connections, tsdb_request_errors_totalopen connections, and replies with an error, by code

docs/metrics.md lists them all.

Backup, export and import

export writes the whole database, or some series, into one file; import reads it into another database. Use it for backups, to move a database to another disk or machine, and when a new tsdb version cannot open the files of an older one (before 1.0 that can happen in a 0.9.x release; the release notes say so).

build/tsdb /data/sensors export -o sensors.tsdbdump      # with the OLD tsdb; also while tsdbd is running
build/tsdb /data/sensors-new import sensors.tsdbdump     # with the NEW tsdb, into a new directory
build/tsdb /data/sensors export --series 'pump7.*' --from 2024-01-01 --to 2024-02-01 | ssh other \
    tsdb /data/sensors import                             # some series and one month, straight to another host
  • The file has what your queries see (deleted rows are gone), with each series' type, retention and state names, and every value exactly as stored. Every later tsdb can import it.
  • import checks the whole file before it writes anything, so a damaged file changes nothing. import --check FILE only checks.
  • Series that already exist are refused, unless you pass --skip-existing, --merge or --replace.
  • Stop tsdbd before you import into its directory.
  • An import into a new directory builds the database beside it and gives it its name only at the end, so an interrupted import leaves no half database under that name.

Moving a database with volumes

Series in volumes keep their volume path in the file. The new database needs volume directories of its own, so tell import where each old volume goes, and add --create-volumes:

# old database /data/sensors with volumes /mnt/nfs1/tsdb/sensors and /mnt/nfs2/tsdb/sensors
build/tsdb /data/sensors export -o /backup/sensors.tsdbdump                 # with the OLD tsdb
build/tsdb /data/sensors-new import /backup/sensors.tsdbdump --create-volumes \
    --volume /mnt/nfs1/tsdb/sensors=/mnt/nfs1/tsdb/sensors-new \
    --volume /mnt/nfs2/tsdb/sensors=/mnt/nfs2/tsdb/sensors-new                # with the NEW tsdb
# or, when all volumes live under one directory, one rule for all of them:
build/tsdb /data/sensors-new import /backup/sensors.tsdbdump --create-volumes \
    --volume-root /mnt/tsdb/sensors=/mnt/tsdb/sensors-new

Then point tsdbd at the new directory, check your queries, and only then delete the old database and its volume directories.
