Operations

What to know when tsdb runs for real: where the data goes, how to read it from other machines, how to guard it against a bad disk, how to watch it, and how to back it up.

Volumes

A database is a directory. A volume is another directory that holds series of their own, for example one per disk or per NFS mount. Each series lives in one volume; you choose it when you create the series.

  • Add one with tsdb DIR volume add PATH, also while tsdbd runs. tsdb DIR volume list lists them, the database directory first.
  • Create a series in it with tsdb DIR create SERIES PATH, or from a client that names the path.
  • Only an operator adds volumes. A client that names a path tsdbd does not know gets "not found", and nothing is created.
  • The path must be absolute, and not inside the database directory or another volume.

Followers, also over NFS

One writer and any number of read-only followers can share a directory. A follower answers queries and sees new data shortly after the writer has it:

build/tsdbd --dir /data/sensors --port 7070
build/tsdbd --dir /mnt/sensors --port 7070 --follow    # a read-only copy that follows the writer

The first line is the writer, the second a follower. The follower looks for new data every 100 ms (--refresh-ms): new parts, merges, and the newest rows from the write-ahead log. The directory can be on NFS, so the followers can run on other machines.

  • When a merge replaces files, the writer keeps the old ones for 8 minutes before it deletes them, so a follower on another machine can finish reading them.
  • Watch tsdb_follow_refresh_age_seconds. Above 5 seconds, the follower has stopped refreshing. It does not tell you that the writer is down; watch the writer for that.
  • An NFS server for tsdb needs some care (sync exports, locks, short leases). docs/nfs-server.md walks through it.

Checksums and the pinned index

tsdb keeps a checksum on every part's header and index, on its write-ahead log and on its small files, and checks them when it opens them. The data blocks themselves are checked only if you ask for it. Whether you should depends on the file system:

File systemStart tsdbd withWhy
ext4 or XFS--verify-checksums, and --pin-index if the RAM is therethey keep no checksums of your data, so without the flag a damaged disk block can come back as wrong values instead of an error. tsdbd reminds you at startup
ZFSnothingZFS checks its data itself

--verify-checksums checks the data each query reads. Each part's index (which rows are where, and the sums, minimums and maximums that queries answer from) is checked when the part is opened, and then read from the file as it is. If the disk damages it after that, answers can be wrong until the next restart refuses the part.

--pin-index keeps a copy of every index in memory, as it was checked, so that cannot happen. The copy costs about 51 bytes of RAM per granule (a block of up to 8192 rows of one series), in the server and in every follower. That is about 4 MB per billion rows of busy series, but at least one granule per series and partition, so with many slow series it adds up: a billion series take about 51 GB per partition. The metric tsdb_pinned_index_bytes shows what it costs. Turn it on where you use --verify-checksums and the RAM is there.

Users, rights and tenants

Clients log in with a user name and a password; the server page explains how. The users live in one file, USERS, in the database directory. Only the file's owner may read it, and it holds no passwords, only values made from them. Such a value is not enough to log in, but together with one recorded login of the same user it is (there is no TLS yet), so keep the file as secret as the data. Whoever can write the directory can add a superuser, so keep it as closed as the data.

Setting up users

Start with one superuser, added before tsdbd first starts. Then give every program and person its own user, with the rights it needs and no more. A collector that only adds data gets insert, not write: if its password leaks, nobody can delete history with it.

build/tsdb /data/sensors user add acme/ingest --password-file /etc/tsdb/acme-ingest.password
build/tsdb /data/sensors user grant acme/ingest insert prefix:acme/
build/tsdb /data/sensors user list
RightWhat it allows
readqueries of every kind, and looking series up
insertwriting rows and creating series (and looking them up, but not reading their rows)
deletedeleting rows and setting retention; replacing a range needs insert too
adminread, insert and delete, plus managing the users named under its prefix
writeshort for insert,delete
SelectorThe series it covers
allevery series
prefix:acme/the names that start with acme/. A prefix is plain bytes: prefix:acme also covers acmecorp/x, so end a tenant's prefix with / (the command line warns otherwise)
name:pump7.flowthat one series
glob:acme/*/temp?the names the pattern matches: * any bytes (also /, also none), ? one byte, \ takes the next byte as it is. At most 64 globs per user

Rights only add up: a user may do on a series what any of its grants allows. There is no way to deny. To take a right away, tsdb DIR user revoke NAME RIGHTS SELECTOR. A series a user holds no right on answers as if it did not exist, so users cannot find out which series other tenants store (only roughly how many: see below).

Tenants and tenant admins

A tenant is a name prefix: acme/ for acme's series and acme's users. A user with admin on prefix:acme/ creates and drops users named acme/..., sets their passwords and gives them rights inside acme/, over the network, without access to the server's files:

build/tsdb /data/sensors user add acme/admin --password-file /etc/tsdb/acme-admin.password
build/tsdb /data/sensors user grant acme/admin admin prefix:acme/
# from any machine that reaches tsdbd, as acme/admin (it asks for acme/admin's password, then the new one):
build/tsdb user add acme/dashboard --server db1:7070 --login acme/admin
build/tsdb user grant acme/dashboard read prefix:acme/ --server db1:7070 --login acme/admin

It cannot give rights outside its prefix, create superusers, or change a user that holds a right outside its prefix.

  • Shares between tenants. Only a superuser grants an acme/ user a right on another tenant's series. After that the acme admins can no longer set that user's password. They may still know the password they set before, so give such a share to a user whose password the tenant admins never set, or set a new one when you share (tsdb DIR user passwd NAME).
  • State names. Series of the state type store labels such as RUNNING in one list per volume. A user with a right on any series of a volume can look up the labels of every series there. Where those labels are sensitive, give each tenant its own volume.
  • Series counts. Series ids are numbered in the order series are created, one count per volume. A user who creates a series sees from its id how many series the volume held, and from two ids how many others created in between. A volume per tenant avoids that too; its path then shows on the metrics port.
  • The network. Without TLS (planned), whoever records a password change made through the server (user add, user passwd) and a later login of that user can log in as that user, and whoever can change traffic can take over a connection after its login. Keep the backend network isolated, and change passwords with tsdb DIR user ... on the server host where you can: that sends nothing over the network.

While tsdbd runs

  • The tsdb DIR user ... commands work beside a running tsdbd; it reads the change within a second. From then on a revoked right is gone on every connection of that user, also those already open, and the open connections of a dropped user get a login error on their next request.
  • A user list that only grows: every change is added at the end of USERS. tsdb DIR user compact rewrites it with one entry per user and grant, also while tsdbd runs.
  • If the last superuser is dropped, tsdbd keeps serving the users that are logged in, but the next start refuses until tsdb DIR user add NAME --superuser has run.
  • Followers read the same USERS and accept no user changes: make them on the writer.
  • If a write to USERS fails, tsdbd stops, as for any file it relies on: an acknowledged revoke must not come back after a crash.
  • export carries series, not users. Copy USERS into the new directory after an import, with tsdbd stopped, or add the users again.
  • Failed logins are counted in tsdb_logins_total{result="failed"} and logged with the user name and the address, at most one line a second.

Metrics

--metrics-port 9170 serves GET /metrics in the Prometheus text format on a port of its own. It is off by default and, unlike the main port, has no login: bind it to a trusted interface. It shows counts for the whole server and per volume, never series names or values; the per-volume counts name each volume's directory, so with a volume per tenant anyone who reaches the port sees those paths and their sizes. A scrape never runs a query. A Prometheus scrape config:

scrape_configs:
  - job_name: tsdb
    static_configs: [{targets: ["db1:9170"]}]

Some of the metrics:

Backup, export and import

export writes the whole database, or some series, into one file; import reads it into another database. Use it for backups, to move a database to another disk or machine, and when a new tsdb version cannot open the files of an older one (before 1.0 that can happen in a 0.9.x release; the release notes say so).

build/tsdb /data/sensors export -o sensors.tsdbdump      # with the OLD tsdb; also while tsdbd is running
build/tsdb /data/sensors-new import sensors.tsdbdump     # with the NEW tsdb, into a new directory
build/tsdb /data/sensors export --series 'pump7.*' --from 2024-01-01 --to 2024-02-01 | ssh other \
    tsdb /data/sensors import                             # some series and one month, straight to another host
  • The file has what your queries see (deleted rows are gone), with each series' type, retention and state names, and every value exactly as stored. Every later tsdb can import it.
  • import checks the whole file before it writes anything, so a damaged file changes nothing. import --check FILE only checks.
  • Series that already exist are refused, unless you pass --skip-existing, --merge or --replace.
  • Stop tsdbd before you import into its directory.
  • An import into a new directory builds the database beside it and gives it its name only at the end, so an interrupted import leaves no half database under that name.

Moving a database with volumes

Series in volumes keep their volume path in the file. The new database needs volume directories of its own, so tell import where each old volume goes, and add --create-volumes:

# old database /data/sensors with volumes /mnt/nfs1/tsdb/sensors and /mnt/nfs2/tsdb/sensors
build/tsdb /data/sensors export -o /backup/sensors.tsdbdump                 # with the OLD tsdb
build/tsdb /data/sensors-new import /backup/sensors.tsdbdump --create-volumes \
    --volume /mnt/nfs1/tsdb/sensors=/mnt/nfs1/tsdb/sensors-new \
    --volume /mnt/nfs2/tsdb/sensors=/mnt/nfs2/tsdb/sensors-new                # with the NEW tsdb
# or, when all volumes live under one directory, one rule for all of them:
build/tsdb /data/sensors-new import /backup/sensors.tsdbdump --create-volumes \
    --volume-root /mnt/tsdb/sensors=/mnt/tsdb/sensors-new

Then point tsdbd at the new directory, check your queries, and only then delete the old database and its volume directories.
