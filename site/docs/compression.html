How compression works

tsdb stores a reading in about 1.2 bytes in our benchmarks (see numbers) where the raw reading takes 12: 8 bytes for the time and 4 for a float32 value. This page shows how, one step at a time. The short version is on the home page.

Blocks of 8,192 readings of one sensor

tsdb keeps the readings of one sensor sorted by time and cuts them into granules of up to 8,192 readings. A granule is the block this page talks about; the code and the logs use that word. The size is the option granule_rows, and it is fixed when the database is created.

A granule holds one sensor only, and with the default one-day partitions (tsdb files its data by day) it never crosses the edge of a UTC day. Granules are written into files called parts: every insert, and every flush of the readings kept in memory, writes parts, and in the background tsdb merges small parts into bigger ones. A granule is stored as two blocks next to each other: first the times, then the values. Each block is packed with its own method, chosen for that granule alone. A sensor that changes its behaviour in the middle of the day gets another method for the later granules.

Why one sensor per block? Neighbouring readings of one sensor look alike: the same pace, the same step size, about the same range. Put two sensors in one block and the pattern is gone. A query for one sensor also reads only the granules of that sensor. Beside the blocks, the part's index keeps one small entry per granule with where it is and a summary of its readings.

Times: steps and changes of steps

A time is a 64-bit number, milliseconds since 1970. Raw, it takes 8 bytes. Sensors report at a steady pace, so the times of a granule are nearly a straight line. tsdb stores the line instead of the numbers.

A steady clock: delta of deltas

The method is called DoubleDelta, or delta of deltas. tsdb stores the first time and the first step, and for every later reading only how much the step changed. The idea comes from the Gorilla paper, and tsdb's version follows the DoubleDelta codec of ClickHouse. A change of 0 is written as a single 0 bit, so a steady clock costs about one bit per reading. A change of up to 64 either way costs 9 bits; bigger changes cost 12, 16, 37 or 69 bits.

Before zstd goes over it (see below), a steady clock is already near one bit per reading. After zstd, the one perfectly regular sensor of our test data (a disk temperature every 60 seconds) needs about 0.03 bits per reading for its times.

A clock that wobbles

Real clocks are off by a few milliseconds. Then the step changes on almost every reading, and DoubleDelta pays at least 9 bits each time. It also makes the noise larger with every subtraction: the change of a wobbling step wobbles several times as much as the wobble itself. So when DoubleDelta needs more than about one bit per reading, tsdb also tries two other layouts, and keeps the one it estimates to be smallest:

  • Grid. Lay a perfectly regular grid over the granule: the first time, then one step apart, with the step taken from the first and last time. Store how far each reading is from its grid point. That is just the wobble, a few milliseconds.
  • Steps. Store each step minus the smallest step in the granule, with no second subtraction.

Both write whole 1-, 2-, 4- or 8-byte words, the narrowest that fits the largest number, and leave the rest to zstd. So the times of a jittery clock are not bit-packed: they are bytes. The layouts are tried only when the block is written with zstd on, which by default means the background merge (see zstd).

Float values: whole-number steps

Values are float32 unless you say otherwise (value types). Raw, a float32 takes 32 bits. Most of the bytes of a database are values, so this is where the most work went.

A sensor measures in fixed steps: a pressure gauge in steps of 0.001 bar, a thermometer in steps of 0.1 °C, or a 16-bit converter that counts and multiplies by a constant. Its readings are whole numbers times a step. tsdb finds that step, stores the whole numbers, and stores them as changes.

Zigzag turns changes that can be negative into plain small numbers: 0, −1, +1, −2, +2 become 0, 1, 2, 3, 4. A small change either way is then a small number, and a small number needs few bits. Here the largest is 4, which fits in 3 bits.

Finding the step

tsdb knows 35 steps: ten-powers from 1 down to 0.0000000001 (11 of them), and powers of two from ½ down to 2−24 (24 of them). The binary steps are tsdb's own. They catch the raw counts of a converter: our vibration test data is 16-bit counts times 2−13, and no ten-power fits that.

Trying 35 steps on 8,192 readings would be slow, so tsdb looks at a sample: four runs of 16 neighbouring readings, spread over the granule. A step costs the bytes its changes need in the sample, plus a penalty for every reading that does not fit it. Ten-powers are tried from 1 downwards, then powers of two from ½ downwards, and the search stops at the first one that gives one-byte changes and no misfits. A step is dropped if more than a quarter of the sample does not fit. If even the best step is not cheap (about 4.5 bytes a reading or more), the granule is not fixed-step and goes to the other methods.

Checking every reading, and the exceptions

The sample only chooses. Then tsdb checks every reading: it computes the whole number, rebuilds the value from it the way the reader will (the number times the step, in double precision, rounded to float32), and compares all 32 bits with the original. A reading that does not come back exactly is an exception: a glitch, a missing value (null), a NaN, a negative zero. It is stored on the side as its position (4 bytes) and its original 32 bits (4 bytes). In the stream of whole numbers its place repeats the number before, so its change is 0 and it does not make the other changes wider. If more than 1 reading in 16 is an exception, the granule is not fixed-step.

Nothing is rounded away: every value comes back with the same bits it went in with.

Packing in groups of 1,024

The zigzag changes are packed in groups of 1,024. Each group has a one-byte header with its width, the number of bits of its largest change, and all 1,024 changes then take exactly that many bits. A group of constant values has width 0 and takes that one byte. Fixed width is what makes the reader fast: unpacking is one short loop per width, with no branches per value. The reader then adds up the changes to get the whole numbers back, multiplies by the step, and puts the exceptions in place.

The result of a granule is: the step, the first whole number (8 bytes), the number of exceptions, the groups, and the exceptions.

What is ALP's and what is ours

This codec is tsdb's own, built on ideas from ALP (Afroozeh, Kuffó and Boncz, SIGMOD 2024, see the papers), the method DuckDB also uses for floating-point columns. From ALP: look at a sample to find the step instead of trying every possibility on every reading; keep the readings that do not fit as exceptions; pack groups of 1,024 at a fixed width. What tsdb added for sensor data: steps that are powers of two as well as of ten; storing the changes between neighbours instead of each number's distance from the smallest in the group; a check in double precision, which has fewer misfits than float32 arithmetic; and the choice per granule.

The change from "distance from the smallest" to "change from the neighbour" matters for slow signals. A disk temperature drifts over a wide range, but each step is small. In tsdb's measurement on that data (docs/design.md, section "ALP, and why it fits sensor data"), ALP's groups needed 6 bits a reading and the changes needed 2.

tsdb also contains ALP itself, as the paper describes it (in float32, as DuckDB does). It is never written to disk. It stays in build/codec-bench as a reference, and it was not smaller than the fixed-step codec on any of our sensor data sets.

When values are not fixed steps

Not every signal is a decimal. A pressure converted from bar to psi and left unrounded is not a whole number times any step. A noisy float is just noise. For these, tsdb has other methods. Each one finds a different kind of pattern:

ALP_rd (ALP's second method)Splits each value into its last bits, which look random and are stored as they are, and its first bits (sign, exponent and the top bits of the digits part, the mantissa), which repeat a lot. Gorilla and Chimp are the well-known XOR methods for floating-point time series (see the papers).

Choosing the smallest

For a float32 granule the choice goes like this:

  1. Fixed steps first. If the fixed-step codec fits, and its result needs 16 bits a reading or less, tsdb keeps it and compares nothing else. (In a merge, the dictionary may still replace it, if the dictionary comes out smaller.)
  2. Otherwise, a contest on a sample. Each of the other methods encodes a sample of 8 KB (16 runs of 128 neighbouring values, spread over the granule), with zstd on top as the real block would have. The sizes are scaled to the whole granule and ranked against the fixed-step result, which counts at any width.
  3. The best, and any within 3% of it, are then encoded in full, and the smallest block is kept.

So "the smallest method per block" means the smallest among the methods tried, judged on a sample first. It is not an exhaustive search, and that keeps writes fast.

The other types

  • float64 uses the same fixed-step idea with wider reach: ten-powers down to 10−15 and powers of two down to 2−30, and exceptions that keep all 64 bits. If a float64 series holds values that were float32 first (widened by a collector), a merge stores the block as a float32 block (an insert does so only when the values are fixed steps), but storing the right type from the start is still better: see value types. When the values are not fixed steps, inserts try Gorilla and byte split; merges also try packed bit delta, ALP_rd and the dictionary.
  • int64 goes through the same integer coder as the fixed-step codec: zigzag changes in groups of 1,024 at a fixed width. It stores plain changes between neighbours, so what a value costs depends on how big the change is, not on how steady: a counter that grows by 1 each time costs a few bits, one that grows by about 1,000 needs about 11 bits before zstd (a steady increment helps only through zstd), and a group of equal values costs one byte. A group whose changes need more than 32 bits is stored with its changes (zigzag) at 64 bits each, not packed.
  • bool and state are small whole numbers and use the integer coder too. A door that changes a few times an hour, or a machine mode that changes every few minutes, comes down to a fraction of a bit per value (see numbers).

zstd, only where it still helps

zstd is a general-purpose compressor. After a block is coded by one of the methods above, tsdb tries zstd on the result (level 1 by default, the option zstd_level) and keeps the zstd version only if it is clearly smaller:

  • the coded block must be at least 64 bytes;
  • for values, zstd must save at least about 3% (1/32) of the block, plus the 4 bytes that record its original length;
  • for times, it must save about 12% (1/8). Every query that reads rows decodes the times, so a small gain is not worth the decoding time.

The block's first byte says which method wrote it (7 bits) and whether zstd was used (1 bit).

When this work is done. To keep inserts fast, a part written by an insert, or by a flush of the readings kept in memory (the memtable), uses the quick set of methods and, by default, no zstd (insert_zstd_level is 0). Times then always use DoubleDelta. Background merges rewrite such parts with the full set of methods and zstd at level 1. A part with nothing to merge with is rewritten alone once its partition has had no new part for 5 minutes (merge_idle_s), or by tsdb_optimize. So the data at rest is the smallest, and fresh data is a little larger for a short time.

Summaries: why queries often skip the unpacking

When tsdb writes a granule, it also computes a summary from the readings, before they are packed, and keeps it in the part's index: the number of readings and of nulls, the first and last time, the sum, the smallest and the largest value, the spread (for the standard deviation), and what time-weighted averages need. The summaries are exact, not estimates: integer sums use 128 bits, so they are never off. The index entries are bit-packed too, at about 32 bytes per granule.

Take "the average per day". A day bucket covers whole granules, so tsdb adds up their summaries and, in most cases, does not unpack them. A granule that a bucket edge cuts is unpacked, and so is one that a delete or the retention limit touched, and one whose times overlap other granules of the same sensor (parts not yet merged, or readings still in memory). The edges of a UTC day fall between granules; the edges of a local day usually fall inside one, so those granules are unpacked, unless the zone is a whole-hour zone and the sensor is busy enough for the hour edges below. Granules are cut with this in mind: they never span two sensors, never cross a UTC day edge in the default layout, and, for a busy sensor (at least 3,000 readings an hour), end at the hour edges too, so that many buckets line up with whole granules.

The sums of float values are added per granule, so they can differ from another order of adding in the last digits. Value types says what that means in practice.

The same bytes on every CPU

A database directory can be copied to another machine, or read by a follower (a read-only copy of the database on another host). So whatever CPU wrote a part, any other CPU must read it, and the same readings must give the same bytes. tsdb works for that on purpose:

  • The portable release (make dist) is built for x86-64-v2 (SSE4.2, CPUs from about 2009 on), and the codecs are built again for v3 (AVX2) and v4 (AVX-512). At startup tsdb picks the best level the CPU has. TSDB_CPU=v2, v3 or v4 picks a lower one. A plain make builds for the machine it runs on and has no levels.
  • All levels must give identical blocks and identical values. So there is no fused multiply-add (-ffp-contract=off), no maths-library function that the C library picks by CPU, float sums are added in one fixed order, and the codecs run in round-to-nearest mode and put the caller's mode back.
  • tests/test_levels.c compares every level the machine has.
