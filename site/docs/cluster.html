Cluster preview

Release 0.11.0 adds replicated and erasure-coded cluster volumes on top of 0.10.0's metadata group. This page sets up a small cluster on one machine, creates a volume, kills the leader, starts it again, and transfers, moves and resets replicas. About ten minutes.

What this is, and what it is not

The metadata group is a few servers that agree, with the Raft protocol, on a list of facts: which servers are members, whether they are up or down, which are voters (they decide) and which only watch, the cluster's settings, its users and their grants (Logins), and the places where volumes, owners, epochs and in-sync sets are kept. A witness is a member with no data: it keeps the list and can vote, a cheap third or fifth vote.

With tsdb cluster volume add, the group places a volume on N servers (its copies) or as an erasure-coded stripe (--redundancy ec=K+M). The leader replicates every write to the in-sync copies before answering; when the leader dies, another copy takes over; copies can be moved, leadership transferred, and lost disks rebuilt from a snapshot.

It is still a 0.x preview. It does not place or move volumes by itself when a server is lost for good (you run volume transfer, volume move or replica reset), and there is no node drain yet. Clients name the volume (tsdbc_series_at) and may send requests to any server. Do not run it in production: the metadata format (version 6) and peer protocol (version 10) may change in a later 0.x release; you then start the cluster again with tsdb cluster init, you do not upgrade it.

Why ship it? The group and replicated volume path are tested with simulators, checkers and fault injection, and now you can run them yourself. Without --cluster none of it runs.

What you need

  • A checkout of tsdb, built with make (the first step does it). Linux, no root.
  • Four free ports for the servers' clients (17081 to 17083 and 17085; the witness of step 9 has none) and five for their peers (17091 to 17095) on 127.0.0.1. If something else uses one, change the numbers in the two lines marked # ports in step 3: they are the only place where the block writes a port.
  • Nothing else. The block only writes under /tmp/tsdb-cluster.

The tutorial

Paste the whole block into a terminal, in the top directory of the checkout. It stops at the first command that fails. Our tests run it word for word, so it works as written.

# 1. Build. Everything lands in build/.
make

# 2. A scratch directory, and the cluster's secret. The secret is a file with 32 random bytes written as hex
#    (mode 0600). Every server and every `tsdb cluster` command reads it. Whoever has it can change the cluster.
D=/tmp/tsdb-cluster
rm -rf $D && mkdir -p $D
build/tsdb cluster secret $D/secret

# 3. Helpers. A "node" is a server with its own data directory (n1/data) and its own state directory (n1/state).
#    The state directory holds the cluster's own files and must be on a local disk, never on NFS.
#    Node N listens for clients on port 1708N and for the other servers on port 1709N (the two lines marked ports).
#    --no-auth: no login, to keep the tutorial short ([Logins](#logins) below shows how). Fine on 127.0.0.1, nowhere else.
#    A witness (node 4) has no data directory and no client port.
port() { echo 1708$1; }                    # ports: the client port of node N
pport() { echo 1709$1; }                   # ports: the peer port of node N
peer() { echo 127.0.0.1:$(pport $1); }     # the peer address of node N
start_node() {                             # start_node N [witness]: start a server, remember its process id
    mkdir -p $D/n$1/state
    if [ "${2:-}" = witness ]; then role="--witness --advertise 127.0.0.1"
    else
        [ -f $D/n$1/data/DISK ] || build/tsdb disk init $D/n$1/data:ssd
        role="--dir $D/n$1/data --allow-shared-device --no-auth --port $(port $1)"
    fi
    build/tsdbd $role --state-dir $D/n$1/state --peer-port $(pport $1) \
        --cluster --cluster-secret-file $D/secret --rack rack$1 >> $D/n$1/log 2>&1 &
    echo $! > $D/n$1/pid
}
status() { build/tsdb cluster status $(peer $1) --secret-file $D/secret; }    # status N: ask node N
wait_for() {                               # wait_for N REGEX: wait (30 s at most) until node N's status has such a line
    for i in $(seq 150); do status $1 2>/dev/null | grep -q "$2" && return 0; sleep 0.2; done
    echo "gave up waiting for: $2"; return 1
}

# 4. Start three servers. They know nothing of each other yet: each one says it is in no cluster.
start_node 1; start_node 2; start_node 3
for n in 1 2 3; do wait_for $n '^node'; done
status 1

# 5. Make the cluster on node 1 (it becomes node 1 and the leader), then add the other two through it.
#    The group grows by itself: one voter, then three. Wait until all three vote, then look at it from node 2.
build/tsdb cluster init $(peer 1) --secret-file $D/secret
build/tsdb cluster node add $(peer 1) $(peer 2) --secret-file $D/secret
build/tsdb cluster node add $(peer 1) $(peer 3) --secret-file $D/secret
wait_for 2 '^group voters 1,2,3 '
status 2

# 6. A volume: in a cluster, data lives in volumes the group places, never in a server's own directory. Add one
#    named plant with three copies, one per node, and wait until every node has made its directory (n1/data/v1, ...)
#    and the group has recorded that it opened it (open_gen). Then write a day of readings into plant through its
#    leader (only the leader takes writes directly; it replicates every write to the other two copies before answering,
#    so all three copies hold the data) and read them back.
build/tsdb cluster volume add $(peer 1) plant --replicas 3 --secret-file $D/secret
for n in 1 2 3; do wait_for 1 "^replica volume 1 node $n rid [0-9a-f]* open_gen 1$"; done
status 1 | grep '^volume\|^replica'
leads=$(status 1 | awk '$1 == "volume" && $4 == "plant" { print $8 }')
echo "node $leads leads volume plant"
TSDB_VOLUME=plant build/client-example 127.0.0.1 $(port $leads)
ls -d $D/n[123]/data/v1

# 7. Kill the leader, as a crash would (kill -9, by its process id). The others elect a new leader, and once that
#    one has led for three seconds (node_timeout_ms) without a heartbeat from the dead node, it marks the node down.
#    Ask a survivor.
leader=$(status 2 | awk 'NR == 1 { print $10 }')
other=$(( leader % 3 + 1 ))
echo "node $leader is the leader: stopping it"
kill -9 $(cat $D/n$leader/pid)
wait_for $other "^member $leader down"
status $other

# 8. Start it again on the same directories. It comes back as the same member with a new incarnation (a counter of
#    its starts), and it is up again.
start_node $leader
wait_for $leader "^member $leader up incarnation 2"
status $leader

# 9. A witness: a member without data. Start it, add it through any member, look at it. With three voters it only
#    watches (the group keeps an odd number of voters); it takes a voter's place when one is lost for good.
start_node 4 witness
wait_for 4 '^node'
build/tsdb cluster node add $(peer 1) $(peer 4) --secret-file $D/secret
wait_for 4 '^member 4 '
status 4

# 10. Hand over, move, rebuild. Node 5 is a fourth data server. Volume 1 (plant) has its copies on 1, 2 and 3.
#     a. transfer: plant's leadership goes to another copy. Writes wait a moment while the old leader sends all it has to
#        the new one, nothing is lost. The command answers when the new leader is in place.
#     b. move: plant's copy on one node moves to node 5, in the background. wait_gone waits for the old copy to go.
#     c. reset: a copy whose disk is lost is refused at its start, with a line that names the command that fixes it.
#        The reset gives it a new identity (a new rid) and the volume's leader sends it a snapshot of the volume.
wait_gone() {                              # wait_gone N REGEX: wait (30 s at most) until node N's status has no such line
    for i in $(seq 150); do
        s=$(status $1 2>/dev/null) && echo "$s" | grep -q '^volumes ' && ! echo "$s" | grep -q "$2" && return 0
        sleep 0.2
    done
    echo "still there: $2"; return 1
}
wait_for 1 '^volume 1 .* isr 1,2,3 '       # the restarted node has caught up and is in sync again
start_node 5
wait_for 5 '^node'
build/tsdb cluster node add $(peer 1) $(peer 5) --secret-file $D/secret
wait_for 1 '^member 5 up .* volumes_ok 1 '
to=$(status 1 | awk '$1 == "volume" && $4 == "plant" { n = split($16, a, ","); for (i = 1; i <= n; i++) if (a[i] != $8) { print a[i]; exit } }')
build/tsdb cluster volume transfer $(peer 1) 1 $to --secret-file $D/secret
wait_for 1 "^volume 1 name plant .* leader $to "
status 1 | grep '^volume 1 '
old=$(( to % 3 + 1 ))                      # a third copy, to move away; the last one stays and is reset below
lost=$(( 6 - to - old ))
build/tsdb cluster volume move $(peer 1) 1 --log --from $old --to 5 --secret-file $D/secret
wait_for 1 '^replica volume 1 node 5 '
wait_gone 1 "^replica volume 1 node $old "
status 1 | grep '^volume 1 \|^replica '
kill $(cat $D/n$lost/pid)                  # the disk of node $lost is lost: stop it, remove the volume's directory, start it
while kill -0 $(cat $D/n$lost/pid) 2>/dev/null; do sleep 0.1; done
wait_gone 1 "^volume 1 .* isr [0-9,]*$lost"
rm -rf $D/n$lost/data/v1
start_node $lost
wait_for $lost '^node'
for i in $(seq 150); do grep -q 'tsdb cluster replica reset' $D/n$lost/log && break; sleep 0.2; done
grep -h 'tsdb cluster replica reset' $D/n$lost/log
build/tsdb cluster replica reset $(peer 1) 1 $lost --secret-file $D/secret
wait_for 1 "^volume 1 .* isr [0-9,]*$lost"
status 1 | grep '^volume 1 \|^replica '
grep -h 'snapshot' $D/n$lost/log
ls -d $D/n$lost/data/v1/*.part | head -n 2

# 11. What the servers said about the leaders and the members' state, from their logs (the details differ on your machine).
grep -h 'leads the metadata group\|proposes node' $D/n[123]/log

# 12. Stop every server by its process id, wait until they are gone, and clean up.
for n in 1 2 3 4 5; do kill $(cat $D/n$n/pid); done
for n in 1 2 3 4 5; do while kill -0 $(cat $D/n$n/pid) 2>/dev/null; do sleep 0.1; done; done
rm -rf $D

Step 11 prints what the servers logged about leaders and members. Only the new leader proposes a change, so a line shows in one log only. For example:

tsdbd: cluster: node 3 leads the metadata group (term 2)
tsdbd: cluster: proposes node 1 down (incarnation 1)
tsdbd: cluster: proposes node 1 up (incarnation 2)

The dead node is down only after a few seconds: a server is marked down when the leader has not heard its heartbeat for node_timeout_ms (3 s by default). The survivors first elect a new leader, and it marks the node down once it has itself led for node_timeout_ms, so the down comes a few seconds after the election. When the down line appears, a new leader exists.

Logins

In a cluster the users and their grants belong to the whole cluster, not to one server: you add a user once, and it can log in on every server. A changed password or a revoked grant counts on every server as soon as the command answers. Start the servers without --no-auth, and give the first superuser to init:

echo 'a long password' > $D/root.pw; echo 'another one' > $D/alice.pw; chmod 600 $D/*.pw
build/tsdb cluster init $(peer 1) --secret-file $D/secret --superuser root --password-file $D/root.pw
build/tsdb cluster user add $(peer 1) alice --password-file $D/alice.pw --secret-file $D/secret
build/tsdb cluster user grant $(peer 2) alice prefix:plant. read --secret-file $D/secret   # any member will do
build/tsdb cluster user list $(peer 3) --secret-file $D/secret
  • tsdb DIR user ... does not work on a cluster server's directory; it names tsdb cluster user.
  • A server that was down refuses logins for a moment after it starts (UNAVAILABLE), until it has heard the cluster: it might still hold a user that was dropped while it was away. The clients do not wait for it: connect again, or to another server.
  • Servers that had their own users before (a USERS file) do not start with --cluster until that file is gone: bring their users in first with tsdb cluster user import, with the servers stopped (the details).

How to read status

tsdb cluster status PEER asks one server what it knows and prints one fact per line. Ask any member: they agree, up to a moment's delay. A server that has just restarted may show its saved copy first, with a stale line, until the group has confirmed it.

LineMeaning
node N mode M role R term T leader L commit C applied AThe server you asked. N: its member number (0: in no cluster). M: none, core (it runs a copy of the Raft group: a voter, or a learner on its way to be one) or watch (it follows the group's state without voting). R: follower, pre-candidate, candidate or leader (- outside the group). T: the election term, up by one at every election. L: the leader's number, 0 when it knows none. C, A: how far the log is committed, and how far this server has applied it.
stale ...The copy this server saved before a restart; no one has confirmed it yet.
cluster UUID replication ... mode M failover F read_barrier B lease_s ... restore_gen RThe cluster's id, settings (init fixes them) and restore generation.
group voters 1,2,3 learners -Who votes, and who is catching up to join the vote.
member N STATE incarnation I addr A peer P rack R heard H ...One line per member. STATE: up or down (the group also knows draining and out, which nothing sets in the preview). I: how many times it has started. A: where clients reach it. P: where servers reach it. H: how long ago the server you asked last heard from it. voter_ok and volumes_ok: whether it may vote and may hold volumes (a witness has volumes_ok 0). core_dropped 1: its Raft core was dropped after a log fault; it goes on as a watcher.
replicated lease_ms ...The settings of replicated volumes (init fixes them).
volume-report ..., domain-report ...Per member, what it says about its volumes and storage domains.
volume N name V uuid U leader L epoch E min_isr M replicas A,B,C isr ... isr_version I set_version S [preferred P] redundancy ...One line per cluster volume: its number and name, leader, copies, in-sync set and redundancy (replicas=N or ec=K+M stripe ...).
replica volume N node X rid R open_gen G [replaces Y]One line per copy: its replica id and open generation (replaces Y while a move is in progress).
volumes N users MHow many volumes and users the group holds.
transfers started ..., moves started ...Leadership transfer and copy move counters from the start of the server you ask.
move volume N node A -> node B: STEP, T sOn the group's leader, one line per move running: its step (catch-up, transfer, shrink, remove) and how long it has run.
peer links KIND: ...Active data-link counts by kind, check level (none, header, full) and transport (tcp, rdma).

How many voters? One with one or two members, three with three or four, five with five or more (at most --voters). A member that does not vote watches.

If something goes wrong

  • "cannot connect to ...: Connection refused": the server is not running (yet), or the address is wrong. Look at /tmp/tsdb-cluster/n1/log. A port that is taken shows there as "cannot listen"; change the numbers in the two lines of step 3 marked # ports, and nothing else.
  • "... is not a cluster peer port with this secret": the address is not a server's peer port, or the secret file differs from the one the server was started with.
  • "the secret file ... is open to its group or to others: refused": chmod 600 it. tsdb cluster secret FILE makes a file with the right mode.
  • "the server is already in a cluster" (from init): stop it, remove its state directory and start it again to start over.
  • "the new server did not answer" (from node add): the server at the new address is not running, or not running with --cluster and the same secret.
  • "the new server belongs to another cluster or has another id" (from node add): the server at the new address is a member of a cluster already. To use it here, stop it, remove its state directory and start it again.
  • The block fails in the middle and servers keep running: stop them by process id: for n in 1 2 3 4 5; do kill $(cat /tmp/tsdb-cluster/n$n/pid); done. Do not use pkill or killall: they stop every process with that name, also ones that are not yours.
  • Two of the three nodes are gone: the third has no majority. Its role stays pre-candidate, it shows leader 0, and the dead members stay up in its view: nobody is left to mark them down. The group changes nothing until one of the others is back. That is the rule, not a bug.
  • When you are done: rm -rf /tmp/tsdb-cluster.

The server: tsdbd options

All of these are off without --cluster. The client port, --dir and every other option work as before.

The command line: tsdb cluster

tsdb cluster with no arguments prints these. The commands talk to a running server's peer address (PEER, host:port), need no directory, keep no state, and authenticate with the secret (--secret-file F).

CommandWhat it does
tsdb cluster secret FILEMake a new secret: 32 random bytes as hex, mode 0600. Never overwrites a file.
tsdb cluster init PEER --secret-file F [options]Make the cluster on one server that is in no cluster yet. It becomes node 1 and the leader. The options fix the settings.
tsdb cluster node add PEER NEW_PEER --secret-file FAdd the server at NEW_PEER (running with --cluster, in no cluster yet). PEER is any member; the command follows to the leader. Adding a member again does no harm.
tsdb cluster volume add PEER NAME [--replicas N | --redundancy ec=K+M|replicas=N] --secret-file FAdd a replicated or erasure-coded cluster volume and open it on the chosen members.
tsdb cluster volume transfer|move|force-leader|gc resume ...Hand over leadership, move a copy in the background, force a leader, or resume EC orphan collection.
tsdb cluster replica reset PEER VOLUME NODE --secret-file FGive a lost or untrusted copy a new replica id and rebuild it from a snapshot.
tsdb cluster user add|passwd|drop|grant|revoke|list|import ...Manage cluster-wide users and grants, or import local USERS files.
tsdb cluster status PEER --secret-file FWhat that server knows (see above).

Options of init; each number is a whole number above 0 (0 turns --leader-balance-s off). Settings for replication, leases, rebuilds and transfers are acted on; those for shared mode (--mode shared, --failover, --lease-s, --read-barrier), --rebuild-after-s and --volumes-per-server are only stored.

What's next

The designs are written; the work goes in this order:

  • The metadata group, finished (S4): names that are unique across the cluster. The servers' links to each other, routing and one-hop forwarding of requests are in this preview. The group's state machine (S1) and what a single server does while its storage is away (UNAVAILABLE, N1) are already in 0.10.0, and users and grants kept in the group are in this preview; the rules for ownership and time come with N7.
  • Replicated mode (R1 to R4) and erasure coding (R5 to R8) are built: each volume on servers with their own disks, with replication, the in-sync set, promotion, transfer, move, snapshot rebuild, and erasure-coded settled parts. Raft stays off the insert path.
  • Shared mode (N0, N2 to N8): a go/no-go measurement (N0), then failover on NFS storage with one writer per volume, fenced by the group. Production on NFSv4 needs this first.
  • Then clients that talk to the volume leader directly, and device classes / storage tiers (R10, R14).

Read more on GitHub: design-ha-modes.md (the two modes and the build plan), design-cluster.md (the replicated cluster and the metadata group), ha.md (failover on NFS) and roadmap.md.
