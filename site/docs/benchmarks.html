Benchmarks

How tsdb 0.9.0 compares with eleven other databases on the same machine and the same data. Every number here comes from the published 0.9.0 results.

How it was measured

  • One machine: AMD Ryzen 9 7950X (16 cores, 32 threads), 64 GB RAM, NVMe disk. One system at a time; every server in a container with the same hard memory limit of 48 GB (InfluxDB 2: 24 GB, and it used at most 8.3 GB).
  • The data: 100 sensors with 1 million readings each, 100 million readings in all, from seven kinds of sensors that behave like real ones (temperatures that creep, tanks that fill and drain, a fast vibration sensor, flows with shutdowns). The size test adds 23 real sensors from a hydraulic test rig: 31 data sets.
  • Every answer was checked against tsdb's before it was timed. Every timing was repeated 5 times; a time is the median time of one request. tsdb ran as a server, over TCP.
  • We left out the questions tsdb answers from the summaries it stores, such as a count over all the data: they measure a lookup, not reading data. Every question below reads the data.
  • A system that ran out of memory or refused a request is shown with the reason. That is a result, not a missing number.

Servers: 100 million readings

100 sensors with 1 million readings each. tsdb ran as a server, over TCP. Ingest is 100 million rows divided by the load time: tsdb syncs every write to disk before it answers; ClickHouse, VictoriaMetrics and QuestDB do not. Read is all 100 sensors over the whole history in buckets of 60 readings, in one request. Max memory is the most each server held without the file cache over the runs that finished, the 16-client runs included; a red tag marks a system that failed with 32 clients asking about many sensors at once.

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. * QuestDB open source, in its default format, which does not compress. It compresses only partitions you convert to Parquet by hand (with ZSTD 1.02 bytes per reading; converting took 28 minutes); automatic conversion is Enterprise only. Exact numbers: BENCHMARKS.md.

Embedded: a library inside your program

The same 100 million readings in one process, with no network. chDB is ClickHouse as a library. Read is random days of one sensor in 5-minute buckets, one call at a time: tsdb uses one thread per call, chDB and DuckDB 32. DuckDB got its readings sorted beforehand (not counted).

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. Exact numbers: BENCHMARKS.md.

100 billion readings: tsdb and ClickHouse

10,000 sensors with 10 million readings each, loaded by 8 streams. Read is the whole table in hourly buckets.

Speed: tsdb is the full bar. Size, time and memory: shorter is better. A box instead of a bar: no number, and why. Exact numbers: BENCHMARKS.md.

Measure it yourself

Clone the repository and run tools/bench-tsdb.sh --quick first to see that it works. It builds an optimized copy, runs tsdb's own benchmarks several times and writes a summary with the mean and spread of every number. The comparison with the other databases is in bench/dbcmp; every single measurement is in 0.9.0-tables.md.
