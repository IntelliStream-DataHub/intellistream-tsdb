The server, tsdbd

tsdbd serves one database directory over TCP. Clients in C, Rust, Python and Java talk to it. It runs one event loop (io_uring, or epoll where io_uring is off) and a pool of worker threads.

Start it

The only flag you must give is the directory: build/tsdbd --dir /data/sensors. It listens on 127.0.0.1, port 7070. The directory is created if it is missing. To listen on another address, add --listen ADDR; there is no encryption yet, so listen on a trusted network only.

It does not start until the database has a superuser, a user who may do everything (see Users and logins below). When it serves, it prints one line, for example:

tsdbd: serving /tmp/tsdb-qs/server on 127.0.0.1:17070, 32 workers, up to 10000 connections, login required, simd avx512, io io_uring

Stop it with kill PID (SIGTERM). It finishes its writes first. To run it as a service, use the systemd unit of the portable tarball.

--partition-ms, --partition-classes and --granule-rows set how a new database lays out its files. They count only when the database is created; the defaults suit most data. Run build/tsdbd with a wrong flag to see the full list.

Users and logins

Every client logs in with a user name and a password. The password never crosses the network: the client and the server prove to each other that they know it (SCRAM-SHA-256, the method PostgreSQL uses). The users live in the file USERS in the database directory, which keeps only a value made from each password, not the password.

tsdbd does not start until there is a superuser, a user who may do everything. Add one with the command line, before the first start:

build/tsdb /data/sensors user add admin --superuser    # asks for the password (or --password-file FILE)

Every other user gets rights on some series: read, insert, delete or admin (write means insert and delete), on all series, on a name prefix (prefix:acme/), on one series (name:pump7.flow) or on a pattern (glob:acme/*/temp?). The operations page shows how to set them up. A series a user may not touch answers as if it did not exist.

The tsdb DIR user ... commands change USERS directly and work while tsdbd runs: it reads the change within a second. Without a superuser tsdbd stops at once with

tsdbd: no superuser: run 'tsdb /data/sensors user add NAME --superuser', or start with --no-auth

With --no-auth nobody logs in and anyone who reaches the port may read, write and delete everything, as in the quick starts of other databases. Use it only on your own machine.

How it uses threads

A small query runs on one thread. A large one, or a request for many series, spreads over more threads, up to --request-threads. Writes that arrive at the same time share one sync to disk.

When the disk fails

If a write or a sync to disk fails, tsdbd stops answering writes and exits with status 1. A retried sync can report success after the kernel has dropped the data, so the only safe step is a restart, which reads back what is really on disk. The metric tsdb_failed shows it; alert on it.

Client timeouts

All four clients give up on a connect after 10 seconds and turn TCP keepalive on, so a server that vanished is noticed about a minute later. A request waits as long as the server takes, unless you set a timeout. After a timeout or a connection error, close the connection and connect again.
